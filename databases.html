Overview

In plain English: The same Travlr travel website, but this enhancement focuses on the database: the part that stores the trips and user accounts.

Travlr is a full-stack travel booking web application developed using the MEAN stack: MongoDB, Express, Angular and Node.js. For the database category, this artifact focuses on the MongoDB and Mongoose portions of the application, including schemas, CRUD operations, indexed fields, validation and database-driven behavior.

This artifact was originally developed in CS-465 Full Stack Development I and is used for the Databases category of the CS-499 Computer Science Capstone.

Enhancement completed

In plain English: In short: the database now rejects bad data, like a price that isn't a number or an invalid email address. It rejects duplicate accounts, keeps the server running when a request is bad, and only lets logged-in users make changes.

The enhancement improved the database layer of the Travlr application:

  • Stronger Mongoose schema validation
  • Improved field types, including perPerson stored as a number
  • Clearer backend controller error handling
  • findOne() for single-trip lookup
  • runValidators: true during update operations
  • Improved JWT-protected database access
  • Duplicate email handling during registration
  • Safer CRUD operations

Enhancement narrative

In plain English: My written explanation, as submitted for the course, of why I chose this project, what I changed, which course outcomes it meets, and what I learned along the way.

Milestone Four: Enhancement Three · CS-499 · June 4, 2026

The artifact I selected for the Databases category is the Travlr Getaways full-stack web application. This project was created during my previous term in CS-465 Full Stack Development I, around March and April of 2026. Travlr is a travel management web application built using the MEAN stack, which includes MongoDB, Express.js, Angular, and Node.js. The application includes a customer-facing travel site and an administrator single-page application that allows authenticated users to manage trip records. For this milestone, I focused specifically on the database layer of the application, including the MongoDB trip and user collections, Mongoose schemas, database validation, database queries, backend error handling, and protected database access.

I selected this artifact for my ePortfolio because it demonstrates my ability to build and improve a full-stack application that stores, retrieves, updates, and protects data. The Travlr application is a strong database artifact because it uses MongoDB to store trip and user records, Mongoose to define schemas and interact with the database, Express controllers to perform CRUD operations, and JWT authentication to protect database write actions. These components show my ability to work with database-backed applications rather than only static or frontend projects. For the enhancement, I improved the artifact by strengthening the Mongoose trip schema with more specific validation rules. I changed the perPerson field from a string to a number so price values are stored in a more appropriate data type. I also added validation for required fields, minimum field lengths, valid image file extensions, positive price values, and trimmed string values. This improved the reliability of the database because invalid records are now rejected at the backend/database level, even if someone bypasses the Angular frontend form validation.

I also improved the database controller logic in several ways. I updated the add trip function so invalid database records return a clear 400 Bad Request response instead of crashing the backend server. I updated the single-trip lookup function to use findOne() instead of find() because the application is searching for one trip by trip code, not a list of trips. This made the database response cleaner and required a small frontend adjustment so the Edit Trip form patches a single returned object instead of using the first item in an array. I also improved update handling by adding runValidators: true to the update operation, which allows Mongoose validation rules to apply when trip records are updated. This prevents invalid update data from overwriting valid database records. In testing, valid POST and PUT requests worked correctly, while invalid requests were rejected with validation errors and did not change the data stored in MongoDB.

In addition to trip validation and query improvements, I improved database security and user data handling. I updated the JWT middleware so protected routes only continue after the token is successfully verified. I tested this by sending requests with a valid token, no token, and an invalid token. The valid token request succeeded, while the missing and invalid token requests returned 401 Unauthorized. This improved the security of database write operations because adding, updating, and deleting trips should only be available to authenticated users. I also improved the user schema by adding email format validation, trimming and lowercasing email values, and adding a minimum length rule for user names. In the registration controller, I added clearer handling for duplicate email addresses and validation errors. This allows duplicate registrations to return a 409 Conflict response and invalid emails to return a 400 Bad Request response instead of failing unpredictably.

This enhancement helped me meet the course outcomes I planned for the Databases category. It supports Course Outcome 2 because I am explaining the database design choices and enhancement process clearly through this narrative. It supports Course Outcome 3 because I evaluated the existing database design and made tradeoff-based improvements, such as using better field types, applying validation rules, and improving query structure. It supports Course Outcome 4 because I used modern full-stack database tools and techniques, including MongoDB, Mongoose schemas, Express controllers, RESTful API routes, JWT authentication, and Postman testing, to improve the functionality and reliability of the application. It also supports Course Outcome 5 because the enhancement strengthened the security mindset of the project. The database layer now validates data more carefully, handles invalid input more safely, protects write operations with improved JWT verification, and avoids exposing protected database operations to unauthenticated requests. I do not have major updates to my outcome-coverage plan because this enhancement still fits the Databases category as originally planned, but it also supports security more strongly than I initially expected.

While enhancing and modifying this artifact, I learned more about the importance of validating data at multiple layers of a full-stack application. In Milestone Two, I improved frontend form validation, but this milestone helped me understand that frontend validation alone is not enough because users or tools like Postman can bypass the frontend and send requests directly to the API. By adding Mongoose validation rules, the database layer now provides another level of protection. One challenge I faced was that invalid trip data originally caused the backend server to crash when Mongoose threw a validation error. I fixed this by adding try/catch blocks and returning clearer JSON error responses. Another challenge was updating findOne() for single-trip lookup because the frontend originally expected an array response. After changing the backend to return a single object, I also had to update the Edit Trip form logic so it worked with the cleaner response. Testing with Postman was especially helpful because it allowed me to verify that valid records were saved, invalid records were rejected, duplicate users were handled correctly, and protected routes required a valid JWT token. Overall, this enhancement improved the Travlr application by making its database layer more secure, reliable, consistent, and professional, while better demonstrating my skills in MongoDB, Mongoose validation, CRUD operations, backend error handling, authentication, and secure data management.

Running the project

In plain English: Instructions for a developer who wants to run the project. Postman is a tool for sending requests straight to the server, and MongoDB Compass shows exactly what is stored in the database.

This artifact is tested through the Travlr backend API, the MongoDB database, the Angular admin application and Postman. Unlike the software design enhancement, the database enhancement requires Postman and MongoDB because the goal is to verify backend validation, database behavior, protected API routes and stored data directly.

Applications and tools needed

Visual Studio Code
Used to open and review the project files.
Node.js and npm
Used to install dependencies and run the Express backend server.
Angular CLI
Used to run the Angular administrator application when testing from the UI.
MongoDB and MongoDB Compass
Used to run the local database and verify stored trip and user records.
Postman
Used to test API requests directly, including valid data, invalid data, JWT-protected routes and duplicate user registration.
Web browser
Used to view the Angular admin interface at http://localhost:4200.

Generated dependency folders such as node_modules were removed to reduce file size, so dependencies must be reinstalled before running the project.

  1. Start MongoDB locally, or confirm the MongoDB service is running.
  2. Install backend dependencies from the main Travlr project folder:
    npm install
  3. Install Angular dependencies:
    cd app_admin
npm install
  4. Start the backend application from the main Travlr project folder:
    npm start
  5. Start the Angular development server in a separate terminal:
    cd app_admin
ng serve
  6. Open the Angular admin application in a browser:
    http://localhost:4200
  7. Open Postman to test the backend API routes directly:
    http://localhost:3000/api/register
http://localhost:3000/api/login
http://localhost:3000/api/trips
http://localhost:3000/api/trips/:tripCode
  8. Open MongoDB Compass to confirm that valid records are saved and invalid records are rejected.

Testing and validation

In plain English: The tests I ran against the database. The codes in the results are standard server responses: 200 or 201 means it worked, 400 means the data was rejected as invalid, 401 means the user isn't logged in, and 409 means the account already exists.

These tests confirm that MongoDB, Mongoose validation, controller error handling, user validation and JWT-protected database access work correctly.

1Start the required services

  1. Start MongoDB locally or confirm that the MongoDB service is running.
  2. Start the backend server with npm start.
  3. Start the Angular admin application with cd app_admin and ng serve.
  4. Open Postman for API testing.

Expected result: MongoDB, the Express backend, Angular and Postman are all ready for testing.

2Valid user registration

  1. In Postman, create a POST request to http://localhost:3000/api/register.
  2. Use this JSON body:
{
  "name": "Database User",
  "email": "databaseuser@test.com",
  "password": "password123"
}

Expected result: The API returns 200 OK with a JWT token.

3Duplicate email registration

  1. Send the same registration request again using the same email address.

Expected result: The API returns 409 Conflict with a message that a user with this email already exists.

4Invalid email registration

  1. Send a POST request to http://localhost:3000/api/register.
  2. Use this JSON body:
{
  "name": "Database User",
  "email": "notanemail",
  "password": "password123"
}

Expected result: The API returns 400 Bad Request with a user validation error.

5Login and JWT token

  1. In Postman, create a POST request to http://localhost:3000/api/login.
  2. Use valid login credentials.
  3. Copy the returned JWT token.

Expected result: The API returns a valid JWT token that can be used for protected trip requests.

6Valid trip creation

  1. Create a POST request to http://localhost:3000/api/trips.
  2. In the Authorization tab, choose Bearer Token and paste the JWT token.
  3. Use this JSON body:
{
  "code": "DBTEST2026",
  "name": "Database Test Trip",
  "length": "4 nights",
  "start": "2026-05-07",
  "resort": "Test Resort",
  "perPerson": 799.99,
  "image": "reef1.jpg",
  "description": "This is a valid database test trip."
}

Expected result: The API returns 201 Created, and the trip appears in MongoDB.

7Invalid trip creation

  1. Send a POST request to http://localhost:3000/api/trips with the same Bearer token.
  2. Use invalid trip data:
{
  "code": "ab",
  "name": "x",
  "length": "y",
  "start": "",
  "resort": "z",
  "perPerson": "abc",
  "image": "reef1",
  "description": "short"
}

Expected result: The API returns 400 Bad Request with a validation error, and the backend server stays running.

8Single trip lookup

  1. Send a GET request to http://localhost:3000/api/trips/DBTEST2026.

Expected result: The API returns one trip object instead of an array, because the backend uses findOne() for single-trip lookup.

9Valid trip update

  1. Create a PUT request to http://localhost:3000/api/trips/DBTEST2026.
  2. Use the Bearer token for authorization.
  3. Use valid updated trip data:
{
  "code": "DBTEST2026",
  "name": "Database Test Trip Updated",
  "length": "5 nights",
  "start": "2026-05-07",
  "resort": "Updated Test Resort",
  "perPerson": 899.99,
  "image": "reef2.jpg",
  "description": "This is a valid updated database test trip."
}

Expected result: The API returns 200 OK, and MongoDB shows the updated trip data.

10Invalid trip update

  1. Send a PUT request to http://localhost:3000/api/trips/DBTEST2026.
  2. Use the Bearer token for authorization.
  3. Use invalid update data:
{
  "code": "DBTEST2026",
  "name": "x",
  "length": "y",
  "start": "",
  "resort": "z",
  "perPerson": "abc",
  "image": "reef1",
  "description": "short"
}

Expected result: The API returns 400 Bad Request, and MongoDB does not overwrite the valid trip record.

11Protected route with no token

  1. Send a PUT, POST or DELETE request to a protected trip route.
  2. Set Authorization to No Auth.

Expected result: The API returns 401 Unauthorized.

12Protected route with a bad token

  1. Send a protected trip request.
  2. Set Authorization to Bearer Token.
  3. Use badtoken123 as the token value.

Expected result: The API returns 401 Unauthorized.

13Valid trip deletion

  1. Create a test trip using the valid POST request.
  2. Send a DELETE request to http://localhost:3000/api/trips/DBTEST2026.
  3. Use the Bearer token for authorization.
  4. Refresh MongoDB Compass or the trip listing page.

Expected result: The trip is removed from MongoDB and no longer appears in the application.
